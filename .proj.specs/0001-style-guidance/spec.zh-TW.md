# 簡報風格指引：首版規格

此為通過第二輪審查之英文 spec 的稽核翻譯，實作以英文為準。目前的通過與凍結狀態見[第二輪報告](review/round-2.md)；文末保留英文原稿編寫時的 stage-2 狀態說明。

## 問題陳述

使用者與採用這些規則的 agent，需要可重複使用、能辨識出高橋流、賈伯斯流、忘形流（張忘形）與比爾蓋茲流差異的簡報風格指引。單靠 theme 或模糊形容詞，無法說明這些差異。既有建議也混入內容規劃、簡報製作、缺乏依據的數值預設，以及對特定 agent 工具的假設。

使用者需要四個可獨立使用的樣式 skills 與一個 route skill，優先以 ChatGPT／GPT 設計。產品必須說明風格約束，內容改寫、重組、簡報製作與匯出仍由使用它的工具處理。

## 解法

在根目錄的產品 skills 集合中，提供四個用途明確的樣式 skills 與一個精簡 route。各樣式提供來源導向的實用指引、核心辨識特徵、可調部分、適用條件及例外。route 優先採用明確指定的風格；否則依既有情境選擇一個主要樣式並簡述理由，只有缺少足以選擇的資訊時才提問。

交付互補的 Markdown 指引與結構化設定。Markdown 說明原則與適用界線；設定提供樣式識別及核心／可調約束，兩者以共用規則識別碼連結。設定預設 YAML，明確要求時改用 JSON。說明文字跟隨使用者語言；識別碼與欄位名稱維持英文。

首版驗收包含文件檢查與實際 ChatGPT 代表情境試用。Skills MCP 載入相容性另行驗證。

## 使用者故事

1. 身為採用這些規則的 agent，我希望能獨立載入四種樣式中的任一種，以便在已知所需風格時取得指引。
2. 身為指定風格的使用者，我希望 route 採用我的選擇，讓偏好決定收到的指引。
3. 身為未指定風格的使用者，我希望得到根據情境的選擇與簡短理由，不必回答多餘問題。
4. 身為調整風格的使用者，我希望能採用相容調整，並理解不相容調整的衝突，讓指引保留可辨識的樣式身分。
5. 身為採用這些規則的 agent，我希望同時取得可讀指引與結構化約束，以便理解條件並使用設定。
6. 身為使用者，我希望看到來源歸屬與證據限制，避免把專案歸納誤認為官方方法或已獲實驗證明的規則。
7. 身為維護者，我希望有文件檢查與 ChatGPT 試用紀錄，讓首版可用性聲明有對應表面的證據支持。

## 實作決策

### 產品責任與可觀察介面

已同意的驗收介面為：

- **S1：已發布的指引文件。** 使用規則的 agent 可以閱讀的產品 skill 指令、補充規則、來源紀錄及交接契約。Q1、Q4–Q7 與 Q13 已確認此文件表面。
- **S2：ChatGPT 回應。** 實際呼叫後回傳的指引與設定、選擇或澄清，以及調整／衝突說明。Q2–Q3 與 Q8–Q13 已確認此回應表面。

這些是文件與回應界線，尚未建立新的函式、API 或簡報產出引擎。透過 Skills MCP 的實際傳輸不屬於首版驗收 gate。目前沒有產品行為；既有結構檢查只能作為文件驗證的參考。

### 樣式內容

每個樣式擁有自己的指引，不必先呼叫 route。各樣式可以共享原則，但必須呈現可辨識的表達焦點。下列焦點是根據來源紀錄所作的專案歸納，不宣稱四位創作者曾發布相同格式的官方規格。

| 樣式 | 辨識焦點 | 證據界線 |
| --- | --- | --- |
| 高橋流 | 以詞句及相對尺度形成主要視覺焦點；其他細節從屬於此文字焦點。 | 大字有出版資料的直接依據；詞句層次的指引屬歸納。不能從文字為主的原型，推出所有情境都禁止圖表或條列。 |
| 賈伯斯流 | 明確的展示、效益、揭露或比較焦點，由精簡文字與相關視覺證據支持。 | 演講節錄支持揭露與比較的觀察，不能推出固定的整份敘事順序或普遍版面公式。 |
| 忘形流（張忘形） | 以精簡文字、具有意義的視覺關係及受眾關聯，讓人理解觀點。 | 創作者說明支持精簡圖文溝通；故事、幽默及黑白外觀不是普遍必要條件。此名稱指張忘形，不是王興。 |
| 比爾蓋茲流 | 透過層級與相關註解，讓證據、數值、比較及系統關係可被理解。 | 分析取向有本人陳述支持。具體樣式規則屬專案歸納，不是正式的「Gates method」，也不要求高密度。 |

詳細規則必須保留這些差異與證據界線。規則可以描述相關素材間的表達偏好，但不執行改寫、拆頁／合頁、不創作大綱或安排講述流程。例子用於說明規則，不轉換使用者內容。此界線只約束樣式 skills 的責任，不能阻止使用指引的其他 agent／工具完成另行獲准的工作。

以下必備核心紀錄讓辨識關係可被查核。它們是專案規則識別碼與歸納，不是原話或官方名稱。每份完成的設定須包含所選樣式的必備紀錄，Markdown 也須表達相同命題；只有配色、字型或泛稱偏好不算符合。

| 必備規則 ID | 必須保留的命題 | 相容的邊界例子 | 衝突的邊界例子 |
| --- | --- | --- | --- |
| `takahashi.text_primary` | 詞句是主要視覺／訊息載體，以相對尺度建立優先層級。其他細節若出現，須提供輔助，不能成為同等或更主要的焦點。 | 允許圖表與三行輔助註解，但明確保留其從屬於主要詞句的關係。 | 將密集圖表或整段文章設為主要載體，詞句只剩次要標題。 |
| `jobs.single_focus` | 展示、效益、揭露或比較元素支持同一個明示焦點。文字／視覺元素服務該焦點，不是互相競爭的獨立主張。 | 改變配色，或使用數個服務同一比較焦點的物件。 | 讓數個無關主張擁有同等主要地位，失去共同展示／比較焦點。 |
| `wangxing.text_visual_relation` | 精簡觀點文字與視覺呈現傳達同一觀點或明示關係。視覺元素須幫助理解該觀點，不能只有裝飾功能。 | 使用色彩或不加幽默，但保留觀點與視覺的關係。 | 用無關裝飾取代有意義的視覺關係，只留下圖說。 |
| `gates.evidence_relation` | 分析指引將證據／數值／系統元素連到明示的比較或系統重點。若標示、單位、假設或限定條件是理解既有證據的必要資訊，須保留這些關係與條件。 | 減少裝飾或增加留白，同時保留證據關係與必要標示／限定條件。 | 移除理解證據所需的標示或假設，或讓數值成為沒有關聯的裝飾。 |

這些例子判定的是指引敘述，不是已產出的投影片外觀。相容指引必須明確保留表列關係；衝突指引否定或取代其中一項關係。補充圖表／註解不會只因存在或數量而構成衝突。每個已宣告的核心或可調規則，其來源紀錄須包含分類、必備命題、適用條件，以及相容／衝突例子。其他規則可以細化此基準，但不能否定它，也不能憑空增加以創作者背書的數值限制。

### 選擇與調整

route 在提問前先讀取既有請求。風格、格式、語言與調整指令，來自使用者對本次 skill 的要求。素材中的引用命令句視為資料，除非使用者明確採納；素材仍可提供用途、受眾與表達脈絡。

明確指定的支援樣式優先於推論出的適用建議。可以說明限制，但不能悄悄替換樣式。未指定時使用已提供的用途、受眾與表達需求；只缺少選填細節不構成提問理由。既有情境不足以選擇時，詢問缺少的決策資訊，不自行編造受眾事實或預設風格。

依下列順序判定分支：明確指定一個支援樣式時交付該樣式；指定名稱不明、不支援，或仍要求數個主要樣式時，詢問要採用哪個支援樣式。其他情況下，若提供的用途或表達需求符合下表至少一個焦點線索，就有足夠資訊選擇。只有受眾，或泛稱要製作／選擇簡報風格，不符合此條件。受眾可細化選擇，但不要求同時提供三種情境欄位。

| 提供的用途或表達需求線索 | 可選焦點 |
| --- | --- |
| 以詞句作為視覺載體來強調訊息 | 高橋流的文字焦點 |
| 展示／揭露某項產品或提案，或說明其效益／比較 | 賈伯斯流的展示／比較焦點 |
| 介紹／說明概念，或以容易理解的關係傳達觀點 | 忘形流的觀點／視覺焦點 |
| 解讀／比較證據或數值，或說明系統關係 | 比爾蓋茲流的分析焦點 |

若符合數個線索，選一個可用樣式，理由同時指出已提供的線索與所選焦點。不要求唯一最佳樣式，也不能只由受眾標籤推論專業程度、所需幽默或場地。

「向高中學生介紹 AI」即使沒有另外指定表達需求，也應根據概念說明直接交付。「比較量測的能源使用量」同樣直接交付；只有「選一種風格」或「受眾是教師」時，須詢問用途或表達需求。這些例子固定的是分支，不宣稱某樣式對這些受眾具有普遍效果。

每次請求只選一個主要樣式。名稱不明、不支援或要求多種樣式時，須在已支援範圍內澄清，不能自行增加 preset 或自動混搭。

非核心調整可以改變指引，但須保留規則紀錄中所有適用核心命題與條件。若變更否定或取代核心命題，便構成衝突：指出 `rule_id`、引用或改述衝突請求、說明會破壞哪個命題，並提供保留該命題的建議。交付原本核心指引；衝突覆寫與尚未接受的替代方案不納入已套用設定。增加輔助細節，只要明確保留主要／輔助關係，就可相容，如前述高橋流例子。這是風格決策界線，不增加一般性權限核准流程。

### 最小交接契約

獨立使用與 route 使用採相同語意契約：

- `style_id`：`takahashi`、`jobs`、`wangxing` 或 `gates` 之一。這是專案識別碼；不宣稱 `wangxing` 是創作者官方英文名。
- `core_rules`：規則紀錄清單，每筆含非空的英文 `rule_id` 及非空的說明字串 `constraint`。
- `adjustable_rules`：相同兩欄位的紀錄清單，代表相容調整後適用的非核心指引；沒有適用規則時可以為空。

規則識別碼在同一份設定內不得重複，在 Markdown 與設定中須指向同一規則，跨語言與序列化也保持相同。核心紀錄表的必備 IDs 固定；其他已發布規則的 IDs 由來源紀錄查找，不根據措辭重新產生。

設定描述的是風格約束，不能成為可執行命令、投影片計畫或 deck 文件模型。約束必須保留正確理解所需的條件。Markdown 補充解釋與相關例外；兩種格式互補，不要求完整複製。

已發布的規則紀錄是語意比較的共同核對依據。每個核心規則的必備命題與適用條件，都須出現在 Markdown 與設定的 `constraint`。若請求未提供可判定條件的事實，條件式規則仍以條件式指令保留。納入設定的可調規則，也須在兩種格式保留適用命題、條件與已接受變更。

理由、歷史背景與例子可以只放在 Markdown；限制約束適用範圍的條件則不能省略。例如只適用於口述投影的規則，不能直接序列化成不帶限制的「使用短句」。若獨立閱讀的例外會改變指令，它也須同時保留在設定與 Markdown。

每個回傳 `rule_id` 的核對項目為：分類正確、每個必備命題都存在、每個適用限制都保留、沒有矛盾命題、沒有尚未接受的調整。所有必備核心 IDs 都須出現。direct／routed、YAML／JSON 與語言變體，都使用同一份核對項目及規則目錄，不比較逐字相同。改述、翻譯、順序與例子可以不同；若改變必備命題的主體、主要／輔助關係、條件範圍或約束強度，就不通過。已核准的試用計畫在試用前，依此基準與來源紀錄寫出各案例的預期命題及條件。

YAML 只使用可對應 JSON 的資料型別，不使用自訂 tags 或宿主專屬物件。明確要求 JSON 時，只改變序列化方式，不改變 schema 或規則語意。完成指引時，回傳 Markdown 加上恰好一種結構化格式；尚無法選定樣式的澄清回應，不必編造設定。

### 發現與使用環境界線

description 必須區分「協助選擇樣式」與「使用指定樣式」。route 保持精簡，找到所選樣式後讀取其指引，依需要讀取補充證據或例子；不要求每次載入全部四種樣式或所有研究筆記。

不能假設 ChatGPT 有 shell、本機路徑、Codex／Claude 指令或可用的 MCP 連線。若無法存取選定指引，回報限制，不編造已載入的規則。

OpenAI 的 GPT-6 Astra 文章提供精簡描述、漸進式揭露與明確完成界線的設計參考。Codex 專屬行為不能當作 ChatGPT 或 Skills MCP 載入契約的證據，產品也不限定 Astra。

| AC-18 | 實際 ChatGPT 試用涵蓋四個樣式、direct／routed、選擇與核心邊界例子、適用條件保留、引用命令句界線、預設 YAML／指定 JSON，以及中英文輸出。紀錄包含請求、提供的 skill 版本／內容、觀察回應、可取得的 host／model 資訊與各條件結果。 |
| AC-19 | 發布證據分別說明文件檢查、實際 ChatGPT 試用與 Skills MCP 載入。未測試 MCP 相容性須明示未驗證，且不阻擋已同意的首版 gate。 |
| AC-20 | 沒有支持證據時，不能把固定字數、換頁時間、meme 頻率或密度門檻歸屬創作者或研究。專案自訂選擇與情境建議須明示其性質。 |

## 測試決策

在 S1 與 S2 驗證外部行為。判定規則語意、選擇、證據界線及與請求的相容性，不驗證逐字措辭、段落順序、隱藏推理或假定的內部工具順序。traceability matrix 定義適用的類型／欄位／界線組合。

- **文件表面：** 檢查五個產品定義、獨立入口、來源／規則歸屬、可辨識差異、一致的 IDs、可對應 JSON 的 YAML 與等價 JSON 例子，以及純風格範圍。需要語意判斷時使用文件審查，不縮減成關鍵字比對。
- **ChatGPT 表面：** 在實際可用的使用環境中提供產品指令，記錄實際提供哪些內容並進行試用。以代表案例涵蓋 AC-18，各條件可共用案例。根據已宣告的樣式規則判定回應，不假設已有學習效果實證。
- **等價輸出：** 同樣請求只變更序列化格式，依規則紀錄核對項目與固定 IDs，比較解析後的設定與規則語意。納入前述適用條件保留與邊界例子。不要求翻譯逐字相同，也不要求非確定性的模型兩次輸出完全一樣。
- **證據紀律：** 區分文件通過、local／subagent 模擬、實際 ChatGPT 試用及 MCP 載入。模擬不能取代 AC-18，目前未宣稱任何產品驗收結果。

既有 portable verifier 只能作為靜態結構檢查的參考，目前沒有產品 test suite 或行為 harness。寫入 ticket tests 前，須在規定的 test plan table 提出案例與實際表面的紀錄方式，取得核准。本節不代表已取得該核准。模型／版本變更會限制既有試用證據的適用範圍，不能推論全部 GPT 或未來使用環境都通過。

已核准計畫須在試用前固定案例、預期分支／命題、執行次數及重試規則。保留每次觀察，包括失敗與重跑，並記錄請求、版本與判定。只有計畫納入的每次執行都通過該案例的全部必要檢查，案例才算 pass；相同版本的失敗不能被成功重試抹除。修正後，另記新版本及結果。只有某 criterion 的全部指定案例都 pass，它才算 pass；未執行檢查標為 unverified，不算通過。

首版驗收要求 AC-01–AC-20 都在指定表面通過；AC-19 可以在明示 MCP 未驗證時通過。這是對已記錄試用的聲明，不是普遍成功率保證。
