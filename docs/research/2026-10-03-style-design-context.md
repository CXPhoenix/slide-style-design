## 四個名稱的證據地位不同

- **高橋流**：有創作者的原始投影片可對照；應抽取可觀察的文字、重點與注意力表達原則，避免從大字外觀推出每頁固定字數或秒數。見[高橋／Jobs 研究](2026-10-03-takahashi-jobs.md)。
- **賈伯斯流**：可由本人演講觀察揭露、比較與視覺聚焦；本次未取得 Jobs 自訂的正式「流派規格」。[Steve Jobs Archive 的演講原文](https://book.stevejobsarchive.com/)可驗證 2007 iPhone 揭露與手機比較，但文字不能證明全部版面與換頁時間。
- **忘形流**：本人明確命名的方法；可以區分創作者自述、原著公開摘錄與課堂心得，避免把後人歸納當成本人規則。見[忘形／Gates 研究](2026-10-03-wangxing-gates.md)。
- **比爾蓋茲流**：本次沒有找到本人自訂的完整同名方法。若保留這個名稱，哪些是本人觀點、哪些是專案設計的分析型風格規則，需要明示。見[忘形／Gates 研究](2026-10-03-wangxing-gates.md)。

## 風格與 theme：待討論的工作區分

以下為訪談用提案，不是已核准的詞彙定義：

- **theme**：配色、字型、背景、共用版面等視覺設定。
- **簡報風格**：訊息如何被強調、文字與圖像如何分工、視覺關係如何讓人理解。Q1 已確定產品提供相關規則，實際內容摘寫、拆合頁與敘事調整由使用這些規則的其他工具處理。

兩者可以重疊。不能從黑底大字就認定是 Jobs，也不能為了區分 theme，反過來認定視覺設定與風格無關。把風格拆為「訊息單位、主次階層、圖文關係、證據呈現、局部／跨頁關係」是本次的分析提案，不是任何人物的官方分類。

## 跨流派參考資料的用途

Assertion-evidence 與多媒體學習研究提供「主張如何由證據支撐」「哪些額外訊息可能干擾理解」的研究脈絡；它們不能直接證明某個人物流派、固定密度值或逐頁混搭有效。參見[研究證據與介面界線](2026-10-03-style-boundaries.md)。

即使不同風格共享同一原則，也不代表它們沒有差異。需從可檢查的表達方式與不適配例子判斷差異，而非只列「簡潔、好看、有故事」等形容詞。

## 第一輪問題

**Q1：你希望「樣式 skill」本身交付哪一層結果？**

- **A．只提供風格規則（建議）**：輸出可供 agent 使用的樣式指引與約束，包含圖文、密度、主次、表達特徵；既有內容的改寫與製作由使用它的其他工具處理。
- **B．也提供內容的風格轉換建議**：可以根據使用者已有內容給出短句、強調方式、圖文搭配等具體建議，保留原本內容順序與頁面切分。
- **C．也能重組既有內容的表達**：允許拆頁、合頁、重排與敘事調整，但仍不製作或匯出簡報檔案。

推薦 A 是為了符合目前反覆確認的純風格範圍；若使用者所指的風格包含實際內容表達調整，B 或 C 也可能符合，需由使用者界定。

**答案：A。** 使用者已確認只提供風格規則。以上 B、C 保留為訪談歷史，不屬於產品範圍。

## 第二輪問題（已回答）

**Q2：route skill 在使用者沒有指定風格時，應如何選擇？**

- **A．只處理明確指定**：使用者說出風格名稱，route 載入對應樣式；未指定時詢問要用哪個風格。
- **B．可依情境自動選擇（建議）**：明確指定時優先採用；未指定時依已提供的用途、受眾與表達需求選擇樣式，簡短說明理由。情境不足時才提問。

此輪只決定選擇方式，尚未決定整份／局部選擇與混搭。

**答案：B。** 使用者已確認可以依情境自動選擇。

## 第三輪問題（已回答）

**Q3：首版 route 的選擇範圍到哪裡？**

- **A．單一風格（建議）**：每次請求選擇一個主要樣式，交付該樣式的規則。
- **B．單一風格＋指定局部例外**：選擇主要樣式，使用者可指定某個章節或頁面角色採用另一樣式。
- **C．自動混搭**：依使用者提供的章節或頁面角色選擇多個樣式，交付各部分的規則與適用範圍。

三者皆只交付風格規則；實際內容改寫與製作由其他工具處理。B、C 的混搭一致性與衝突處理需後續確認。

**答案：A。** 使用者確認首版採單一風格，並要求後續訪談使用可點選的選擇題。

## ChatGPT／GPT 指引的補充依據

來源：[Rethinking skills and prompts for GPT-6 Astra](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)，OpenAI，Eric Provencher，2026-09-11；2026-10-03 已閱讀正文。

文章直接建議精簡且準確的 description、漸進式揭露、減少過度細密的操作配方，並明確定義任務邊界與完成條件。文章主要討論 Codex 與 coding agents；其中的 Codex description 縮短機制不能直接當作 ChatGPT 或 Skills MCP 的行為證據。

以下是本專案的設計歸納，仍待具體設計與驗證：

- route 保持精簡，選定樣式後才載入該樣式；來源詳情與例子按需要閱讀。
- 各樣式以核心特徵、可調部分、適用條件與例外表達規則，避免增加角色扮演或固定操作步驟。
- description 明確區分選擇風格與提供指定樣式的用途，避免五個 skills 因模糊觸發條件而全部載入。
- 指引應能由 ChatGPT 理解與使用，不預設 shell、本機相對路徑或 Codex／Claude Code 專屬指令；Skills MCP 的載入方式須依實際工具契約設計。
- 完成條件限於交付所選樣式的指引與必要的選擇／衝突說明；不延伸成簡報製作流程。

## 第十輪問題（已回答）

**Q10：Markdown 與結構化設定要如何分工？**

- **A．互補（建議）**：Markdown 說明原則、適用條件與例外；結構化設定提供樣式識別、核心約束與可調項目，方便接手的 agent 使用。兩者共用規則識別碼以保持一致。
- **B．完整對等**：兩種格式都包含完整規則與例外；任一格式都能單獨使用，接受較長輸出與同步維護成本。

此輪只決定雙格式的資訊分工；具體欄位與 YAML／JSON 語法仍待確認。

**答案：A。** 使用者確認採互補分工，兩者共用規則識別碼以保持一致。

## 第十一輪問題（已回答）

**Q11：結構化設定預設採用哪種語法？**

- **A．YAML（建議）**：方便在 ChatGPT 對話中閱讀與調整；需要工具解析時，須以支援 YAML 的解析器處理。
- **B．JSON**：適合程式直接解析；對話中閱讀與手動調整較繁瑣。
- **C．預設 YAML，明確要求時改用 JSON**：兩種語法共用相同欄位與語意，每次只輸出一種結構化格式。

此輪僅決定風格設定的序列化格式，不增加工具整合或簡報製作責任。

**答案：C。** 使用者確認預設 YAML，明確要求時改用 JSON；兩者共用相同欄位與語意，每次只輸出一種結構化格式。
